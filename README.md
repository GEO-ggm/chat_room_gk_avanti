# chat_room — тестовое задание Flutter Middle+

Экран чата `room1`: история из 7 сообщений, отправка новых через локальный асинхронный метод, статусы `pending / sent / failed` и ручной повтор после ошибки с тем же `clientId`.

## Окружение

| | Версия |
|---|---|
| Flutter | **3.50.0** (stable), закреплена в `.fvmrc` |
| Dart | **3.14.0** |


Android-часть проекта сгенерирована, но на устройстве не проверялась.

Зависимости: из сторонних пакетов только `flutter_riverpod` (^3.5.0), без кодогенерации.

## Архитектура

Простая feature-first структура без лишних слоёв: общий транспорт лежит в `core`, всё, что относится к чату, — в `feature/chat`.

```
lib/
├── main.dart                         точка входа: ProviderScope + MaterialApp
├── core/
│   └── api/
│       └── chat_api.dart             FakeChatApi (имитация сервера), chatApiProvider,
│                                     SendException, константы chatId / currentUser
└── feature/chat/
    ├── chat_screen.dart              UI: ChatScreen, MessageBubble, _MessageFooter,
    │                                 шторка действий, MessageInput
    ├── logic/
    │   └── chat_provider.dart        ChatController (Notifier) + chatControllerProvider
    └── model/
        └── message.dart              Message, MessageStatus
test/
├── chat_controller_test.dart         unit-тесты ChatController
└── chat_screen_test.dart             widget-тесты: пустой ввод, повтор и удаление через шторку
```

Связи между слоями:

```
ChatScreen ──watch──▶ chatControllerProvider (ChatController)
    │                         │
    └──read.notifier──▶ send / retry / delete
                              └──read──▶ chatApiProvider (FakeChatApi)
```

- **Интерфейс** — только `feature/chat/chat_screen.dart`. Виджеты подписываются на `ref.watch(chatControllerProvider)` и вызывают `send` / `retry` / `delete`. Бизнес-логики в виджетах нет.
- **Логика и состояние** — `feature/chat/logic/chat_provider.dart`. Здесь создаются сообщения, переключаются статусы и проверяется, можно ли повторить отправку.
- **Транспорт** — `core/api/chat_api.dart`. Отвечает только за историю и за «отправку» с задержкой.
- **Модель** — `feature/chat/model/message.dart`: неизменяемый класс с `copyWith`.

## Принятые решения

- **Источник истины** — `ChatController extends Notifier<List<Message>>`. Список неизменяемый: каждое изменение создаёт новый список, и Riverpod перестраивает только подписанные виджеты.
- **clientId** назначается при создании сообщения (`c-<microseconds>-<seq>`, без пакета uuid) и не меняется при повторах. Все обновления идут через `_update(clientId, ...)`, который заменяет запись на месте, поэтому дубли невозможны.
- **serverId** выдаёт «сервер» после успешной отправки. Он хранится отдельно от `clientId`, у исторических сообщений совпадает с их id.
- **Правило ошибок** в `FakeChatApi`: счётчик попыток `Map<clientId, int>`. Первая попытка для каждого `clientId` после задержки (800 мс) бросает `SendException` — до «сохранения» на сервере. Все последующие попытки успешны.
- **Блокировка повтора**: `retry` выполняется только из статуса `failed`. Статус `pending` выставляется синхронно до `await`, поэтому повторное нажатие во время запроса не запустит второй запрос. В UI действия доступны только у `failed`: тап по иконке ошибки или по самому сообщению (`GestureDetector`) открывает шторку «Повторить отправку / Удалить». Контроллер берётся до `await showModalBottomSheet`, поэтому действие выполнится, даже если пузырь успел пересобраться.
- **Удаление**: `delete(clientId)` убирает запись из списка, тоже только из статуса `failed`.
- **Пустые сообщения**: кнопка отправки неактивна при пустом вводе или вводе из одних пробелов. `send()` дополнительно проверяет `trim().isEmpty` и возвращает `false`.
- **Пузырь сообщения**: ширина до 80% экрана. Под текстом справа — время (`HH:mm`, без пакета intl) и статус своего сообщения: `pending` — спиннер, `sent` — галочка. При `failed` слева от пузыря показывается красная иконка ошибки. Слот статуса фиксированного размера, поэтому при смене статуса строка не сдвигается.
- **Жизненный цикл**: после `await` проверяется `ref.mounted`, чтобы не обновлять состояние уничтоженного провайдера.
- **Тестируемость**: `FakeChatApi` подменяется через `chatApiProvider.overrideWithValue(...)`, поэтому в тестах задержка короткая.





## Ручная проверка (F4)

| Проверка | Ожидаемый результат |
|---|---|
| Пустой ввод / только пробелы | кнопка отправки неактивна, запись не создаётся |
| Новое сообщение | сразу появляется в ленте со статусом `pending` (спиннер) |
| Первая попытка | статус `failed`: слева от пузыря красная иконка ошибки, приложение остаётся доступным |
| Тап по иконке ошибки или сообщению | открывается шторка «Повторить отправку / Удалить» |
| Повтор | та же запись переходит в `pending`, затем в `sent` (галочка); во время запроса шторка не открывается |
| Удаление | запись с ошибкой исчезает из ленты |
| Дубли | после повтора в ленте одна запись с тем же `clientId` |
| Отправленное сообщение | тап по нему шторку не открывает |

Эти сценарии также покрыты автотестами в `test/`.

## Ограничения

- История хранится только в памяти: нет пагинации, локальной БД и восстановления после перезапуска (по ТЗ).
- Нет потока входящих событий, ACK/echo, синхронизации, push-уведомлений и звонков (по ТЗ).
- Удаление локальное: сообщение с ошибкой не было сохранено на «сервере», поэтому запрос не нужен.
- Текущий пользователь захардкожен (`me`), чат один (`room1`).
- Проверено только на iOS.
